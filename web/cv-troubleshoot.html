Order of operations Start here

When CV disappoints, the temptation is to immediately jump to "add more data" or "try a fancier algorithm." Resist that. The cheapest fixes usually come first. Work through this order:

What to try, in order of cheapest to most expensive

  1. 1. Run Imbalance Comparison first (costs nothing) The Model Lab has a "Compare Imbalance Strategies" button that trains your variant 5 ways side-by-side. Class imbalance is the single most common reason for poor F1 and it is the cheapest fix. Always check this before touching the algorithm or collecting data.
  2. 2. Try a different algorithm (costs one CV run) Logistic Regression is the right starting point, but it assumes linear separability. If your comment/no-comment boundary is non-linear, Random Forest or Gradient Boosting can gain 5–15 F1 points with zero extra data. Run CV again with the new algorithm — same variant, same strategy.
  3. 3. Inspect domain buckets (costs nothing) If one fold is the outlier, use "Inspect Domain Buckets" to see which sites landed there. A single dominant domain with unusual patterns can tank a whole fold. Understanding this tells you whether the problem is fixable with data or structural.
  4. 4. Collect more labeled data (costs real time) Only do this after exhausting the above. If the learning curve shows that more data would still help (train–test gap is still large at full training size), then labeling is worth it. If the curves have converged, more data will not meaningfully improve F1.
  5. 5. Review label quality (costs real time but fixes the root) If F1 is stubbornly low across all algorithms and strategies, and you have plenty of data, mislabeled examples are often the culprit. A 5–10% label noise rate can suppress F1 by 0.05–0.15. Score some items with your best model and review the high-confidence mistakes.

High variance: folds disagree High std

📊
What you see in the CV table F1 std is above 0.08–0.10. The 95% confidence interval is wide (e.g. [0.60–0.82]). Individual fold F1 values range widely, e.g. 0.61, 0.78, 0.82, 0.79, 0.75.
Why this happens
Each fold tests on a different set of domains. High variance means the model's performance is highly sensitive to which domains end up in the test set. Some domain clusters are genuinely harder (foreign-language sites, sites with very few comment-section examples, sites where comment pages look structurally identical to non-comment pages). The model is not bad — it just faces an easier test in some folds than others.
1
Inspect domain buckets — find the weak fold

Click "Inspect Domain Buckets" in the Diagnostics panel. Look at the bucket that corresponds to your lowest-F1 fold. What domains are in it? Are they all from the same niche? Are there very few labeled rows? This tells you whether the problem is structural or fixable with data.

2
Collect more labeled data from the weak bucket's domains

If the weak fold has 3× fewer comment-section examples than the others, the model is not learning those patterns. Label more examples from those domains specifically. Even 50–100 extra rows from the right domains can dramatically tighten the folds.

3
Accept it if the domains are structurally different

If the weak bucket contains foreign-language sites or a completely different content type, no amount of data from your existing distribution will fix it — the model genuinely cannot generalise there. In that case, document it and consider whether those domains should be in scope at all. The mean F1 across the other 4 folds is your real number.

How much variance is acceptable? Std below 0.05 is comfortable. Std of 0.05–0.09 is worth investigating but not disqualifying — proceed with caution and note the weak fold. Std above 0.10 means the model is too sensitive to the test distribution to trust; diagnose before training the final model.

One fold is dramatically worse Outlier fold

⚠️
What you see in the CV table Four folds cluster tightly (e.g. F1 around 0.80–0.84) and one fold is an outlier (e.g. F1 = 0.52). The overall std is high because of that one fold.
Why this happens
Domain buckets are assigned by hash(hostname) % 5. This is deterministic and fair, but it cannot guarantee equal difficulty. One bucket might contain a site that accounts for 40% of all comment-section pages in your dataset — so when that bucket is the test set, the training distribution shifts dramatically and the model struggles. Or the bucket might simply have too few labeled rows to evaluate reliably.
1
Open "Inspect Domain Buckets" and look at the outlier bucket

Check: how many domains? How many labeled rows? What is the comment rate? If one domain dominates the bucket (e.g. 80% of the rows), that domain's characteristics are controlling the fold's difficulty.

2
Check whether the outlier fold has very few test rows

If the weak fold's test set has fewer than ~100 labeled rows, the F1 measurement is noisy anyway — a handful of wrong predictions swings it wildly. Look at the "Test" column in the per-fold table. If it is small, the low F1 may just be statistical noise from tiny sample size.

3
Label more rows specifically from that bucket's dominant domain

If one site controls a bucket and it is genuinely hard, more labeled examples from that site go into the training set of the other folds — the model will learn its patterns and the weak fold will improve on next CV.

4
Try Gradient Boosting — it handles domain-specific pattern shifts better

Logistic Regression uses a single global linear boundary. If one domain cluster requires a different decision boundary, it will always underfit that cluster. Tree-based models can learn domain-specific subregions of the feature space.

Low F1 across all folds Systematic failure

This is a different problem from high variance. All folds agree: the model is just not good. The diagnosis path depends on what else the CV table tells you.

❓ Is ROC-AUC above 0.80 across all folds?
YES → The model can rank pages with comments above pages without — it just doesn't threshold well. This is a class imbalance problem, not a feature problem. Jump to Section 5 and try imbalance strategies.
NO → The model cannot even rank correctly. Continue below.
❓ Do you have fewer than ~500 labeled examples total?
YES → The model is almost certainly data-starved. With fewer than 500 rows split across 5 folds, each fold trains on only ~400 rows and tests on ~100. That is not enough. Label more before anything else.
NO → Data volume is not the issue. Continue below.
❓ Are you using Logistic Regression?
YES → Try Random Forest or Gradient Boosting. LR assumes a linear decision boundary. If pages with comments and pages without overlap in feature space in a non-linear way, LR will always underfit. Tree-based models can find complex boundaries.
NO → Continue below.
❓ Are you using the right variant for the sites you are targeting?
YES → Check label quality. If ROC-AUC is low despite a good algorithm and enough data, mislabeled examples are the most likely cause. See Section 9.
NO → Switch to the variant whose features match your content type. The "keywords excluded" variant removes text features — use it only for non-English or keyword-agnostic detection. The standard variants include all signals.

Good ROC-AUC, bad F1 Imbalance problem

📈
What you see in the CV table ROC-AUC is 0.88–0.92 across all folds (strong). But F1 @0.50 is 0.55–0.65 (weak). The Best F1 ★ is much higher (0.75–0.80), achieved at a threshold of 0.20–0.35.
Why this happens
ROC-AUC measures ranking quality — does the model put pages with comments above pages without in its probability scores? F1 measures classification quality at a specific threshold. A large gap between the two means the model ranks correctly but its probabilities are compressed toward the middle — it is not confidently pushing comment-section pages toward 1.0. This is classic class imbalance: when no-comment pages outnumber comment-section pages 10:1, the model's "safe" bet is to output moderate probabilities for everyone, which destroys F1 at 0.50 but leaves ranking intact.
1
Run "Compare Imbalance Strategies" — this is exactly what it is for

The comparison trains your variant 5 ways (Baseline, Class Weighted, Undersample, Oversample, SMOTE) and shows F1/Precision/Recall side by side. Pick whichever strategy improves F1 the most without collapsing Precision.

2
Try Class Weighted first — it is the safest option

It does not add or remove rows — it just tells the optimizer to penalise comment-section misses more heavily. No data fabrication, no information loss. Almost always better than Baseline when comment:no-comment ratio exceeds 1:3.

3
If Class Weighted is not enough, try SMOTE

SMOTE creates synthetic comment-section examples by interpolating between real comment-section rows in feature space. It can push the model's comment probabilities higher, closing the gap between F1 @0.50 and Best F1 ★. Check that Precision does not fall too far.

4
If nothing helps, accept that the threshold will just be low

If ROC-AUC is high, the final model will have a good threshold curve — the system will automatically find the right threshold (e.g. 0.28) during training. The production scanner uses that threshold, not 0.50. Low F1 @0.50 in CV does not mean the deployed model will perform poorly.

The imbalance strategies explained Quick reference

Every strategy is a different answer to the same question: "How do we stop the model from being lazy and predicting no comments for everything?"

Strategy What it does Best when Watch out for
Baseline Does nothing. Trains on the raw labeled data as-is. Classes are roughly balanced (ratio under 1:3). Use as a control run. F1 will be poor if imbalance is significant.
Class Weighted Multiplies the loss for comment-section misses by the imbalance ratio. No rows are added or removed. Any imbalance level. The safest first step. No data mutation. Logistic Regression uses true loss weighting. Other algorithms use a weighted bootstrap approximation, which is noisier.
Undersample Majority Randomly removes no-comment rows until comment:no-comment is 1:1. You have so many no-comment pages that the model never sees diverse comment-section examples. Also faster training. Throws away no-comment data. The model may not learn to distinguish borderline no-comment pages from comment-section pages.
Oversample Minority Duplicates real comment-section rows until classes are balanced. You have very few comment-section examples and cannot afford to throw away no-comment data. Identical duplicates — the model memorises specific comment-section rows rather than generalising. SMOTE is usually better.
SMOTE Creates synthetic comment-section rows by interpolating between real comment-section examples in feature space. Severe imbalance (1:5 or worse). When Oversample causes overfitting. When Class Weighted is not strong enough. Synthetic rows can sometimes look like no-comment pages if comment-section examples are very scattered. Inspect Precision after applying.
The practical starting sequence: Baseline → Class Weighted → SMOTE. Run "Compare Imbalance Strategies" once and it tests all five simultaneously so you do not have to do them one by one. Pick the strategy where F1 is highest and Precision does not fall below a level you can live with in production.

Switching algorithms Which to pick

Changing the algorithm is often the second-highest-leverage move (after imbalance strategy). Here is how the five available algorithms differ in practice for this problem:

Logistic Regression

  • Fastest to train
  • Most interpretable
  • Linear decision boundary
  • Calibrated probabilities
Start here. Always your baseline. Underperforms when comment/no-comment boundary is non-linear.

Random Forest

  • Handles non-linearity well
  • Robust to outliers
  • Slower than LR
  • Good with high-dimensional features
Try when LR F1 plateaus and variance is still high. Can overfit on very small datasets (<500 rows).

Gradient Boosting

  • Often highest F1
  • Handles complex interactions
  • Slowest to train
  • Most sensitive to small datasets
Best when you have 1,000+ labeled rows and want peak F1. Slow. Can OOM on large datasets in the worker.

Decision Tree

  • Very fast
  • Fully interpretable
  • Low depth = underfits
  • High depth = overfits badly
Mostly useful for understanding which features matter. Almost never the right production choice on its own.

Neural Network (MLP)

  • Can learn complex interactions
  • Slow to train
  • Needs more data than tree models
  • Sensitive to feature scaling
Worth trying when Gradient Boosting has plateaued and you have lots of data. Often no better than Gradient Boosting for tabular feature data.
One rule of thumb: When moving from LR to RF or Gradient Boosting, keep the imbalance strategy the same for the first comparison. Changing both at once makes it impossible to know which change helped. Change one thing at a time and re-run CV.

Reading the learning curve Diagnose the gap

The learning curve trains on fractions of your data (10%, 25%, 50%, 75%, 100%) and tracks Train F1 vs. Test F1 at each size. The shape of the gap tells you exactly what is wrong.

Pattern 1 — Persistent gap at 100%

Train F1 stays high (0.90+) while Test F1 stays low (0.65). The model is memorising training data but not generalising. This is overfitting.

10% train
10% test
100% train
100% test

Fix: Use a simpler algorithm (LR instead of RF). Add more data. Or both.

Pattern 2 — Gap closes as data grows

Train F1 and Test F1 converge as you add more data. More data is genuinely helping. The gap has not fully closed at 100% yet.

10% train
10% test
100% train
100% test

Fix: Collect more labeled data. It will still help.

Pattern 3 — Curves converge and are both high

Train and Test F1 are both strong and close together at full data. The model is generalising well. Data saturation is reached.

10% train
10% test
100% train
100% test

Action: Train the final model. More data will not help much. Consider better features if you need further improvement.

Pattern 4 — Both curves are low and converged

Train F1 and Test F1 are both low (below 0.65) and track each other closely. The model is not overfitting — it just cannot learn from these features.

10% train
10% test
100% train
100% test

Fix: The features are not discriminative enough. This is a feature engineering or label quality problem — not a data volume problem. More rows will not help.

When data quality is the real problem Hard to spot

Label noise is the sneakiest problem because it looks exactly like "the model is bad." If you have tried different algorithms and strategies and F1 is still stuck, the labels themselves may be inconsistent.

🔍
Signs of a label quality problem ROC-AUC is stuck below 0.78 despite enough data and algorithm variety. Train F1 and Test F1 are both low and converged (Pattern 4 above). The model keeps misclassifying the same types of items across all algorithms.
Why this happens
If 5–10% of your comment-section examples are actually labeled as no-comment (or vice versa), the model is trying to learn a boundary that does not exist. No algorithm can find a pattern that is not there. Label noise above ~5% is enough to suppress F1 by 0.05–0.15 and ROC-AUC by 0.04–0.10.
1
Score your labeled dataset with your best-performing model

Train the final model with your best config. Then score every labeled item. Look at high-confidence errors: items your model scores as comment-section=0.92 that are labeled no-comment. These are your mislabeling candidates. Review them manually.

2
Focus on the "confident mistakes" — not the borderline ones

A model scoring something 0.95 and being wrong about it is much more suspicious than scoring something 0.55 and being wrong. The high-confidence mistakes are the ones most likely to be label errors, not hard examples.

3
Correct and re-run CV

Even fixing 20–30 mislabeled examples can unlock a 0.05–0.08 F1 improvement because it removes contradictory signal that was confusing the model across all folds.

The hard truth about label noise: There is a theoretical upper bound on F1 given a certain noise rate. If 10% of your comment-section examples are mislabeled, the best F1 you can ever achieve is roughly 0.90 — no algorithm overcomes that. Improving labels is often worth more than any algorithmic change.
