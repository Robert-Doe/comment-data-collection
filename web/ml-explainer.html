1. What the Metrics Actually Mean

The model's job is to look at a candidate region on a webpage and answer: is this a comment section? Every prediction is either right or wrong, and there are four ways it can go:

Model says: Positive (comment) Model says: Negative (not comment)
Actually Positive True Positive (TP) — correct hit False Negative (FN) — missed it
Actually Negative False Positive (FP) — false alarm True Negative (TN) — correct rejection

Precision

Of everything the model flagged as a comment region, what fraction actually was? 

Precision = TP / (TP + FP)

High precision means low false-alarm rate. A model with 100% precision never flags something that isn't a comment. But it could achieve this trivially by flagging almost nothing — missing real comment sections left and right.

Recall

Of all the real comment regions that exist, what fraction did the model actually find? 

Recall = TP / (TP + FN)

High recall means the model finds most of the real comment sections. 48% recall means the model was missing more than half of all real comment regions on the test set. That's the number that matters most for this product — a missed comment section is a failed detection.

F1 Score

The harmonic mean of precision and recall. Harmonic mean punishes extreme imbalances more than arithmetic mean.

F1 = 2 × Precision × Recall / (Precision + Recall)

A model that has 100% precision and 1% recall gets an F1 of about 2% — terrible, even though precision looks perfect. F1 is the headline metric for imbalanced classification problems.

ROC-AUC

Area Under the Receiver Operating Characteristic curve. It measures the model's ability to rank positives above negatives, regardless of what threshold you use. An AUC of 1.0 is perfect; 0.5 is random guessing.

The test ROC-AUC was 0.9272 — very good. This tells us the model's probability scores are genuinely informative. The problem wasn't the model's ability to discriminate; it was the threshold used to convert those scores into yes/no decisions.

Key insight ROC-AUC 0.9272 with recall 48% means the model could discriminate well, but the decision boundary was in the wrong place. Fixing the threshold alone is expected to raise recall significantly without retraining.

3. Overfitting and Domain Holdout

What overfitting is

A model overfits when it memorises the training data instead of learning the underlying pattern. It learns which specific domains happen to have comment regions rather than learning what features make a region look like a comment section.

training.com/post
seen during training
→
99% probability
newsite.com/post
never seen before
→
38% probability — missed

The model learned domain identity, not comment structure

Why domain holdout makes the test so hard

The train/test split in this codebase uses a domain holdout: every URL on example.com goes to either train or test — never both. This is intentional. It reflects reality: in production, the model will constantly encounter new websites it has never seen.

A random 80/20 split would give inflated metrics because both splits would contain URLs from the same domains. The domain holdout gives an honest picture of how the model generalises to new websites.

Trade-off Domain holdout is the right split for measuring real-world performance, but it makes training harder. The model must learn features that transfer across websites, not just patterns specific to seen domains. That's exactly why we need regularisation, dropout, and early stopping.

The three causes of the gap

CauseEffectFix applied
Too many epochs (200, fixed) Model keeps fitting training domains past the point of generalisation Early stopping with patience=20
Weak regularisation (L2=0.0001) Weights can grow large to memorise specific domain signals L2 raised 10× to 0.001
No dropout Hidden neurons co-adapt to each other on training domains 20% inverted dropout on hidden layers

4. Why 0.5 Was the Wrong Threshold

After training, the model outputs a probability between 0 and 1. A threshold converts that probability into a yes/no decision. The code was using the naive default of 0.5.

Why 0.5 fails on imbalanced data

In this dataset, comment regions are the minority class. The model's raw probabilities are calibrated to the training distribution: if 20% of candidates are positive, the model will naturally output scores clustered below 0.5 even for genuine positives, because the prior probability of being positive is low.

Using 0.5 as the cut-point on an imbalanced dataset systematically discards low-confidence positive predictions that may still be correct. The result is high precision (you only flag things you're very sure about) but very low recall (you miss anything the model was less than 50% confident about).

The threshold curve shows this clearly. At different thresholds on the same model:

ThresholdPrecisionRecallF1
0.2061%81%70%

0.50 (old default)82.6%48.0%60.7%

Illustrative values based on ROC-AUC 0.9272 model. Exact numbers depend on the retrained model.

The fix: optimal threshold from training data

After training, the code now sweeps all thresholds from 0.01 to 0.99 on the scored training rows (never the test holdout — that would be data leakage) and selects the one that maximises F1 on those rows. That threshold is stored in the artifact and used as the default for both metric reporting and the deployed runtime bundle.

Why train rows, not test rows? If you chose the threshold that maximises F1 on the test set, the test metrics would be artificially inflated — you'd be tuning to the holdout. Using train rows to pick the threshold is the honest approach: it's information the model has already seen, so it's not leakage, and it still transfers to unseen data because we're only choosing a scalar cut-point, not changing any weights.

5. Early Stopping

Before this fix, the neural network always trained for exactly 200 epochs regardless of whether the model was still improving. After epoch ~80 on a domain holdout split, the model typically stops getting better on unseen domains and starts memorising the training domains harder. The extra 120 epochs are pure overfitting.

How it works

The training data is split again inside the neural network: 85% is used for gradient updates (fit set), and 15% is held out as a validation set used only to measure the loss — never for weight updates.

Service.js
train split (80%)
→
NN fit set (85%)
weights updated here
placeholder
→
NN val set (15%)
loss measured here

Service.js test set (20%) is never touched inside the NN at any point.

After every epoch, the validation loss is measured. If it hasn't improved for 20 consecutive epochs (the patience), training stops and the weights from the best-seen epoch are restored.

Why 15% / patience 20?

15% of ~11,000 training rows = ~1,650 examples — enough to get a reliable loss estimate each epoch. Patience 20 allows the optimiser to pass through short plateaus without stopping prematurely, while still catching the moment generalisation starts to degrade.

What you'll see in the trace Each trace entry now records both loss (fit set) and val_loss (validation set). When early stopping fires, training_options.early_stopping will be true and stopped_epoch will be less than epochs.

6. L2 Regularisation

Regularisation adds a penalty to the loss function that discourages large weights. The idea: if a weight has to be very large to fit the training data, it's probably exploiting noise specific to those examples rather than a genuine signal. 

Loss = Binary Cross-Entropy + λ/2 × Σ w²

The λ (lambda) term is the L2 coefficient. The old default was 0.0001. It has been raised to 0.001 — 10× stronger.

What this does in practice

Larger L2 keeps weight magnitudes smaller. Smaller weights mean the model is less able to assign extreme probabilities to examples just because they match a memorised training-domain pattern. The model is forced to rely on features that are consistently predictive across many domains, not just one.

L2 = 0.0001 (old)L2 = 0.001 (new)
Weights can grow to ±10 or higher to fit training domains Weights are penalised heavily for growing past ±2–3
Model very confident on training domains Model more cautious, better calibrated on new domains
Train F1 ~98%, Test F1 ~61% Train F1 will drop; Test F1 expected to improve
The trade-off Stronger regularisation deliberately hurts training performance. If you see the train F1 drop from 98% to 88%, that's not a bug — it's the model being prevented from memorising training domains. The goal is test F1, not train F1.

7. Dropout

Dropout is one of the most effective regularisation techniques for neural networks. During each training batch, a random fraction of hidden neurons are silenced (their output set to zero). Dropped neurons contribute nothing to that forward pass and receive no gradient update.

Input (73 features)
→
Hidden 1 (32 neurons)
~6 neurons zeroed
→
Hidden 2 (16 neurons)
~3 neurons zeroed
→
Output (sigmoid)

Zeroed neurons change randomly each batch. Output layer is never dropped.

Why this helps generalisation

Without dropout, neurons can co-adapt: neuron A learns to detect a signal, and neuron B learns to correct for A's errors on the training data. This co-adaptation means the pair works well together on training domains but neither generalises independently.

With dropout, neuron B can't rely on A being present. Every neuron must learn to be useful on its own. The result is a more robust set of features that generalise better to new domains.

Inverted dropout

The implementation uses inverted dropout: surviving neurons are scaled up by 1 / keepProb (e.g. with 20% dropout, by 1/0.8 = 1.25). This keeps the expected value of each neuron unchanged, so the network sees the same activation scale during training and inference. At inference time (prediction), dropout is disabled entirely — no scaling is needed because inverted scaling was already done during training.

Dropout rate 0.2 20% of hidden neurons are dropped each pass. Common values are 0.2–0.5. Lower values are safer for smaller networks and smaller datasets. With only 32 and 16 hidden neurons, 20% is conservative but impactful.

8. The RAM and 504 Problems

The 504 timeout

The browser POSTs to /api/modeling/train and holds that HTTP connection open while the server trains the model. If training takes longer than the proxy's timeout (Caddy: 120 seconds), the proxy kills the connection and returns 504. The training keeps running server-side — the model gets saved — but the browser already received an error.

Browser POST /train
→
120s… Caddy kills it
→ 504

Even though training finishes server-side at 3 minutes, the browser sees an error

The fix: POST /train now responds in <1ms with { jobId }. Training runs as a detached background promise. The browser polls GET /train-status/:jobId every 3 seconds. No HTTP connection is ever held open long enough to time out. It doesn't matter if training takes 30 seconds or 30 minutes.

The 6 GB heap crash

The training pipeline loads all labeled items from the database (up to 14,000+ rows with full HTML content, candidate text, screenshots paths, etc.) into a JavaScript array before feature extraction begins. All of this sits in the same heap as the API server. When combined with the feature extraction intermediate objects and the neural network's gradient computation, the process exceeds Node.js's default heap limit and crashes — taking the API server down with it.

Memory fix: pre-allocated gradient buffers

The neural network training loop was allocating fresh gradient accumulation arrays on every mini-batch. With 14,000 rows ÷ 32 batch size = 437 batches per epoch × 200 epochs = 87,400 allocation events, each creating a cluster of short-lived arrays. The GC had to track and collect all of these, inflating the heap and causing fragmentation.

The fix: allocate the gradient buffers once before the epoch loop and reset them to zero at the start of each batch with fill(0). Same result, a fraction of the GC pressure.

Why the async fix also protects against OOM crashes

With training running as a detached promise: if training does OOM and the process crashes, the API server is restarted by Docker without any data loss. But more importantly, if training is running in the background and OOMs, the background promise dies, the job status in memory is updated to error, and the browser's next poll shows the error message. The API server continues to handle other requests. The user gets a clear error instead of a 503 / connection refused.

How to verify the improvements

  1. Open Model Lab → Train Variants and train a Neural Network with the default settings. The new defaults (L2=0.001, dropout=0.2, early stopping) are active without any configuration change.
  2. Watch the elapsed time counter — training now happens server-side. No more 504.
  3. When it completes, compare the Test Recall and Test F1 to the previous 48% / 60.7%.
  4. Check training_options.early_stopping and stopped_epoch in the artifact JSON — these tell you whether early stopping fired and how many epochs it actually trained for.
  5. The optimal_threshold field in the artifact tells you what threshold the model decided on. Compare it to 0.5 — it will almost certainly be lower.
