1. The Fundamental Separation: Weights vs Threshold

A trained neural network (or logistic regression, or any classifier) does two completely separate things that people often treat as one:

73 input features
from the candidate region
→
Model weights
learned during training
→
Probability score
e.g. 0.34
→
Threshold
is 0.34 ≥ 0.28?
→
YES / NO

The weights are fixed after training. Changing them requires running gradient descent again — a full retrain.

The threshold is just a number you compare the probability against. You can change it at any time, on any saved model, in milliseconds. The model doesn't need to know you changed it. You're not touching any of the learned weights — you're just moving the line that says "this probability is high enough to count as positive."

Key point Changing the threshold is not cheating, not retraining, and not modifying the model. It's choosing where on the precision–recall tradeoff curve you want to operate. Different use cases need different operating points — this is normal and expected.

2. What the Threshold Curve Already Stores

Every model artifact that gets saved to disk already contains a threshold_curve field. This was computed at the end of training by scoring every row in the test set, then sweeping all 101 thresholds from 0.00 to 1.00 in steps of 0.01 and recording what happens.

Each of the 101 entries looks like this:

{
  "t":         0.28,       ← the threshold being evaluated
  "precision": 0.741,      ← TP / (TP + FP) at this threshold
  "recall":    0.734,      ← TP / (TP + FN) at this threshold
  "f1":        0.737,      ← harmonic mean of precision + recall
  "accuracy":  0.889,      ← (TP + TN) / total
  "tp":        94,         ← true positives
  "fp":        33,         ← false positives
  "fn":        34,         ← false negatives
  "tn":        601         ← true negatives
}

This means every model on disk already has the full answer to "what would my metrics be if I used threshold X?" stored in the artifact JSON. No recomputation needed. No rescoring needed. No retraining needed. You just read the curve, pick the entry you want, and apply it.

The PR curve shown in the threshold tuner UI is drawn directly from this stored data. Every time you drag the slider, you're reading from the threshold_curve array that was saved when the model was trained.

3. Why 0.5 Was Costing You 30+ Points of Recall

The previous reported metrics were computed at threshold 0.5 — the default that every classifier uses unless told otherwise. For a balanced dataset where half the examples are positive, 0.5 is often reasonable. This dataset is not balanced.

Comment regions are the minority class. When the model sees a candidate, the prior probability that it's a comment region might be 15–25%. The model's raw output reflects this: even for a genuine comment region, the model might output 0.31 or 0.38 — a probability well above chance, clearly ranking this candidate above most negatives, but still below 0.5. With a 0.5 threshold, that confident positive prediction is silently discarded as negative.

0.001.00

A score of 0.30 is well above chance for an imbalanced dataset — but 0.5 calls it negative.

The result: the model's ROC-AUC was 0.9272 — it was ranking positives above negatives very well. But because the threshold was too high, most of those well-ranked positives were still called negative. Recall sat at 48%.

The threshold curve for this model already shows that at threshold ≈ 0.28–0.32, F1 is substantially higher than at 0.50. The model hadn't changed. The data hadn't changed. Just the decision line needed to move.

4. The Four Optimization Modes

"Optimal" depends on what you're optimizing for. The tuner exposes four strategies, each picking a different point on the threshold curve.

Mode What it maximises Formula Use when
F1 (default) Harmonic mean of precision and recall 2·P·R / (P+R) You want a balanced operating point. Good general default.
Recall Fraction of real positives found TP / (TP+FN) Missing a comment section is worse than a false alarm. You're willing to review more FPs to find everything.
Precision Fraction of flagged items that are correct TP / (TP+FP) Every flag triggers a manual action and false alarms are expensive. You'd rather miss some real positives than have FPs.
Youden's J Sensitivity + Specificity − 1 Recall + TN/(TN+FP) − 1 You want to treat both positive and negative detection symmetrically. Standard in medical/diagnostic statistics.
None of these are objectively "correct" They reflect different priorities. The right mode depends on what happens downstream when the model makes a mistake. For a comment detection system where missing a comment section means a failed scrape, recall is usually the most important metric. For a moderation system where a false positive removes valid content, precision matters more.

Youden's J in plain English

Youden's J statistic is the threshold where the model is equally good at detecting positives (high sensitivity/recall) and rejecting negatives (high specificity = low false positive rate). It's the point on the ROC curve furthest from the diagonal random-guess line. If you don't have a strong opinion about recall vs precision, Youden's J is a principled default.

6. What "Apply This Threshold" Actually Does

When you click Apply, the browser sends a single HTTP request: 

PATCH /api/modeling/models/{artifactId}/threshold
Content-Type: application/json

{ "threshold": 0.28 }

The server then does exactly four things:

  1. Load the artifact from disk Reads the full .json file for this model from the artifacts directory.
  2. Find the nearest curve point The threshold curve is stored at 0.01 intervals. If you asked for 0.283, it snaps to the nearest stored point (0.28). Reads the precision, recall, F1, TP, FP, FN, TN directly from that curve entry — no rescoring needed.
  3. Write two fields back to the artifact Updates optimal_threshold and replaces evaluation.test.candidate_metrics with the values from the curve point. Everything else in the artifact (the model weights, the full threshold curve, the feature reliance, the training options) is left completely unchanged.
  4. Save and respond Writes the updated artifact back to the same .json file in place. Returns the new threshold and metrics as JSON. The browser refreshes the model list to show the updated numbers.

The effect is immediate and permanent (on disk). If you retrain the model, the new training run will compute a fresh optimal_threshold from the train rows and overwrite this value. But the patch persists across server restarts, page reloads, and any other request that reads the artifact.

The runtime bundle picks this up automatically When you download a Runtime JSON from the model, the thresholds.positive field now defaults to optimal_threshold from the artifact instead of the hardcoded 0.5. If you've applied a tuned threshold, the runtime bundle will use it without any extra steps.

What if you want to auto-pick without dragging the slider?

The PATCH endpoint also accepts an optimize field instead of an explicit threshold. The server reads the stored curve and finds the best point for the chosen metric automatically: 

PATCH /api/modeling/models/{artifactId}/threshold
{ "optimize": "f1" }       ← max F1
{ "optimize": "recall" }   ← max recall
{ "optimize": "precision" }← max precision
{ "optimize": "youden" }   ← max Youden's J

7. The Honest Caveat: Test Curve vs Train Curve

The threshold_curve stored in every artifact was computed from the test rows — the held-out domains that the model never saw during training. This means:

  • If you pick the threshold that maximises F1 on this curve and then report "my test F1 is X%", you've used the test set to choose a hyperparameter (the threshold). The reported number is slightly optimistic — the true F1 on genuinely new data will be a little lower.
  • This is sometimes called threshold leakage. It doesn't corrupt the model weights. It only affects whether the reported metrics are a fully honest estimate of future performance.

What the code does to avoid this

The training pipeline (since the recent update) computes the optimal threshold from the train rows — not the test rows — and stores it as optimal_threshold in the artifact. The test metrics in the artifact are then reported at this train-derived threshold. This gives you an honest estimate of test performance because the threshold was selected without looking at the test set.

Bottom line For the existing model with 48% recall: use the slider, pick max F1 or max recall, apply it. The reported metrics will be slightly optimistic but the deployed model will genuinely perform better on new data than it did at threshold 0.5. For future models, the threshold is now derived from train rows automatically — no manual tuning needed and no reporting bias.

Nothing was retrained Every change described in this document operates on the probability outputs of an already-trained model. The weights inside the model are read-only throughout. Threshold tuning is fast (milliseconds), reversible (just PATCH again with a new value), and can be done on any model that has a stored threshold_curve — which is every model trained by this system.
