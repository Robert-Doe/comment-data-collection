Detecting the Right Comment Container:
Homogeneity Approaches

A detailed comparison of two strategies for teaching the extension to prefer the outer top-level comment list over nested reply sub-threads — and why the reply-keyword feature deserves its own signal entirely.

1 The Core Problem

The model keeps scoring a nested reply sub-thread higher than the top-level comment list. Both are structurally similar — a container of repeated, uniform children — but we want the outermost one.

// What a typical comment section looks like in the DOM div.comments-list ← WE WANT THIS (top-level UGC region) div.comment img.avatar span.username p.text div.replies ← Model keeps picking THIS instead div.reply div.reply div.reply div.comment ... div.comment ...

Why does div.replies often score higher? Three compounding reasons:

  1. Tighter homogeneity. Reply items are simpler (just text + username). The outer comment items are heterogeneous: they mix avatar, username, text, metadata, reaction buttons, AND the replies section. More variety = lower homogeneity score.
  2. Higher child-count density. A reply thread might have 8 children in a tight container. The outer list has 30+ children but they're richer — the feature extractor may reward compactness.
  3. Training data bias. If training data was labeled on pages where the "comment section" was itself a tight thread (e.g., Reddit threads, forum posts), the model learned to associate tight homogeneous lists with UGC, regardless of nesting level.
Key Insight The problem is not that the reply container isn't a UGC region — it is. The problem is we want the outermost meaningful UGC region, not an inner sub-region, because that's what a developer targeting "the comment section" expects.

2 Approach 1 — Ancestor Penalty (Post-Hoc)

After scoring all candidates, walk each candidate's pseudo-node parent chain. If any ancestor is also a candidate scoring above UGC_LOW_THRESHOLD, multiply the child's score by 0.6. 

// Three-pass classify() — simplified

// Pass 1: score everything into rawScores
for (const candidate of candidates) {
  rawScores.set(candidate.id, scoreCandidate(candidate));
}

// Pass 2: walk pseudo-node parent chain
for (const candidate of candidates) {
  let score = rawScores.get(candidate.id);
  let parentId = PseudoDOM.nodes.get(candidate.id)?.parentId;
  while (parentId) {
    const ancestorScore = rawScores.get(parentId);
    if (Number.isFinite(ancestorScore) && ancestorScore >= UGC_LOW_THRESHOLD) {
      score *= 0.6;  // penalise — an ancestor is also a candidate
      break;
    }
    parentId = PseudoDOM.nodes.get(parentId)?.parentId;
  }
  finalScores.set(candidate.id, score);
}

// Pass 3: write finalScores to ugcRegionMap
Pros
  • Simple — no feature extractor changes, no retraining
  • Works immediately on the current model
  • Handles any nesting depth transparently
  • Tunable multiplier (0.6 → 0.3 for stricter penalty)
Cons
  • Blunt — penalizes ALL nested candidates, even legitimate ones
  • Depends on pseudo-node parent linkage being accurate
  • Doesn't help when the outer container itself is not detected at all
  • Compound penalty issue: a reply-of-reply gets penalised twice (×0.6×0.6 = ×0.36)
  • Doesn't teach the model anything — the bias remains in weights

When the Ancestor Penalty Misfires

Case A — "Featured + All Comments" layout

div.comments-section ← scores 0.72, becomes candidate div.featured-comments ← scores 0.81, gets penalised to 0.49 ✗ div.comment (but this IS the real high-quality UGC!) div.comment div.all-comments ← scores 0.78, gets penalised to 0.47 ✗ div.comment div.comment div.comment

The outer div.comments-section is a layout shell, not a real UGC region. But it scores high enough to trigger the penalty on both real inner regions, missing both.

Case B — Hacker News flat threading

div.comment-tree ← outer wrapper, scores 0.65 div.comtr ← each comment IS the reply, indented by CSS div.comhead penalised even though there's no real nesting div.comment-text div.reply-link (just a link, not a sub-list) div.comtr ...

Here there is no reply sub-thread. The nesting in the DOM is purely structural (each div.comtr is itself a candidate), but the penalty falsely fires because div.comment-tree is also a weak candidate.

Case C — Infinite Reddit-style nesting

div.comments ← depth 0 — score 0.74 div.reply-list ← depth 1 — score 0.81 → penalised to 0.49 div.reply-list ← depth 2 — score 0.79 → penalised to 0.47 div.reply-list ← depth 3 — score 0.77 → penalised to 0.46 div.reply-list ← depth 4 — score 0.75 → penalised to 0.45

Each level gets penalised relative to its parent — compound penalties spiral quickly. Legitimate deep threads in Reddit or phpBB could be missed entirely.

3 Approach 2 — Depth-Windowed Homogeneity (Feature-Level)

Instead of correcting scores after the fact, change how homogeneity is measured so that the outer comment list naturally outscores the inner reply container in the first place. The idea: measure child uniformity at multiple depth levels, weighting shallower depths more heavily and tolerating divergence at deeper levels. 

/**
 * Returns a composite homogeneity score for `element` up to `maxDepth`.
 * Depth 1 (direct children) is weighted 1.0.
 * Each subsequent depth is weighted at half the previous.
 *
 * A "signature" for a node is tagName + dominant class tokens (sorted).
 * Homogeneity at a level = fraction of nodes sharing the most common signature.
 */
function depthWindowedHomogeneity(element, maxDepth = 3) {
  let totalScore = 0;
  let weight = 1.0;
  let currentLevel = [element];

  for (let d = 0; d < maxDepth; d++) {
    const nextLevel = currentLevel.flatMap(n => [...(n.children || [])]);
    if (nextLevel.length < 2) break;  // not enough nodes to judge

    const signatures = nextLevel.map(n => nodeSignature(n));
    const freq = new Map();
    for (const sig of signatures)
      freq.set(sig, (freq.get(sig) || 0) + 1);
    const dominant = Math.max(...freq.values());
    const homo = dominant / nextLevel.length;

    totalScore += homo * weight;
    weight *= 0.5;   // each deeper level counts half as much
    currentLevel = nextLevel;
  }

  // Normalise so max possible score is 1.0
  // (geometric series: 1 + 0.5 + 0.25 = 1.75 for maxDepth=3)
  const maxPossible = (1 - Math.pow(0.5, maxDepth)) / (1 - 0.5);
  return totalScore / maxPossible;
}

function nodeSignature(node) {
  const classes = [...node.classList]
    .filter(c => !//(is-|has-|active|selected|loaded)/.test(c))  // strip state classes
    .sort()
    .slice(0, 3)           // cap at 3 tokens to reduce over-specificity
    .join('.');
  return `${node.tagName}${classes ? '.' + classes : ''}`;
}

Critical Limitation Reply threads are structurally simpler than comment lists — they have fewer child types at every depth. Depth-windowed homogeneity will therefore still give them a higher raw score. The approach alone doesn't solve the problem without a second signal that says "this element is a reply context, not a primary list."
Pros
  • Model learns the right thing — feature encodes semantic structure
  • Tolerates developer variance at deep levels (weight tapers off)
  • No post-hoc correction logic needed
  • Generalises — trained once, works across sites
Cons
  • Requires retraining the model
  • Reply threads still outscore outer lists on raw homogeneity
  • Needs a complementary signal to distinguish reply contexts
  • maxDepth tuning required — too deep = slow, too shallow = misses signal

4 Where Developers Put Reply Threads

The depth at which a reply container appears in the DOM varies enormously by site, framework, and developer preference. This is precisely why a rigid "only penalise if nesting depth > 2" rule would fail. Here are the real-world patterns:

Pattern A — Flat Siblings reply at depth 1

Replies are siblings of top-level comments, not children. Visual indentation is done with CSS padding-left. Used by: Hacker News, older phpBB, some Django/Flask blog setups.

div.thread ← target: contains everything div.comment[data-depth="0"] ← top-level comment div.comment[data-depth="1"] ← reply (sibling, not child!) div.comment[data-depth="2"] ← reply to reply (also sibling) div.comment[data-depth="1"] ← another reply to root div.comment[data-depth="0"] ← next top-level comment

In this case the ancestor penalty would never fire because there IS no nested reply container — but the outer div.thread contains both comments and their replies mixed at the same level. The homogeneity at depth 1 looks perfect because all children share the same div.comment signature.

Pattern B — Direct Child Container reply at depth 2

Each comment element contains a div.replies directly. The most common pattern. Used by: YouTube comments, Facebook, most React comment components.

section.comments article.comment header.comment-header div.comment-body ul.replies ← reply container at depth 2 li.reply li.reply article.comment ...

Pattern C — Wrapper-Wrapped reply at depth 3

A wrapper div separates the comment body from the reply region. Common in WordPress with custom themes, Shopify review apps.

div.comment-list div.comment-item div.comment-body div.comment-footer ← likes, share, report div.comment-thread ← wrapper ul.reply-list ← reply container at depth 3 li.reply-item li.reply-item div.comment-item ...

Pattern D — Framework Shell Layers reply at depth 4–5

Vue/React component trees add wrapper elements for every component boundary. A comment component wraps a thread component wraps a list component. This is common on Disqus, Discourse, and modern SPA-based review platforms.

div[data-component="comments"] div[data-component="comment"] div.comment-root div.comment-content div.comment-text div.comment-actions div.replies-region div[data-component="reply-list"] ul.replies ← reply container at depth 5 li.reply li.reply

Pattern E — Infinite Nested Threading reply at N+1

Reddit (new), some forums, and GitHub PR review threads allow recursive nesting. A reply container can appear at any depth because a reply can itself have replies.

div.comments depth 0 div.thread depth 1 — top-level thread div.comment div.children depth 2 — 1st-level replies div.comment div.children depth 3 — 2nd-level replies div.comment div.children depth 4 — 3rd-level replies div.comment div.children depth 5 — ...
Key Takeaway Because reply containers appear at depth 1 through 5+ depending on the site, any approach that uses DOM depth as a heuristic (e.g., "penalise if depth > 3") will break on real sites. The signal must come from content/semantics, not position in the tree.

5 Crazy Edge Cases

Edge Case 1 — Review Sites with Q&A Inside Reviews

Amazon, Yelp, and Tripadvisor embed a mini Q&A or "seller response" section directly inside each review. Both the outer review list and the inner Q&A have high homogeneity. The ancestor penalty would suppress the Q&A entirely, but an analyst might want BOTH regions exported.

div#reviews ← 40 reviews → want this div.review div.review-body div.review-photos div.questions ← 6 Q&A items → also want this (separate UGC type!) div.question div.question

Edge Case 2 — Shopify with Multiple Review Apps

A store uses two review widgets: Yotpo in the main product tab and Okendo in a "Community" tab. Both are at completely different DOM depths and have incompatible class name schemes. Neither will be a descendant of the other. Both are valid top-level UGC regions and should both score high without penalty.

Edge Case 3 — Twitter/X Style "View replies" Lazy Load

The reply list doesn't exist in the DOM until the user clicks "View 14 replies." On initial load, the outer div.timeline scores high and gets detected. After expansion, a new div.replies injects into the DOM as a candidate with higher homogeneity. The ancestor penalty would retroactively suppress it after classification — but was it right to suppress it?

Edge Case 4 — Comments Inside Modal / Drawer

Figma, Linear, and Notion-style apps show comments in a side panel that is a completely separate DOM subtree from the main content. The outer container is a portal (div#modal-root) which is not an ancestor in the pseudo-DOM parent chain. The ancestor penalty never fires, which is correct — but depth-windowed homogeneity might also miss the portal if the feature extractor doesn't traverse into portals.

Edge Case 5 — Shadow DOM Components

Disqus and some web-component-based comment widgets use Shadow DOM. The pseudo-DOM cannot see inside shadow roots, so the candidate is the host element (div#disqus_thread) with no visible children. Homogeneity at depth 1 is 0. Both approaches fail entirely here — this requires a separate "known widget host" signal.

Edge Case 6 — Single Comment with Many Replies (Viral Post)

div.comments-list ← 2 comments. Low child count → low score? div.comment Comment A: 1 reply div.replies div.reply div.comment Comment B: 87 replies (viral) div.replies ← 87 uniform children → scores very high div.reply ×87

The outer div.comments-list only has 2 direct children, so its depth-1 homogeneity is based on a tiny sample. The ancestor penalty fires on the 87-reply thread inside, suppressing it. But that reply thread is arguably the richest UGC source on the page. You'd want it detected, or at minimum not suppressed.

Edge Case 7 — Comment System Built With a Table (Legacy CMS)

Old Joomla, legacy Drupal, and some WordPress themes use <table> layouts for comments. Each row is a comment. The reply rows are visually indented via a spacer <td>. Homogeneity-based detection fails because each <tr> has a different number of <td> children (the spacer shifts the count for nested replies).

Edge Case 8 — Comments Mixed with Ads

Many mobile sites inject ad units every 3–5 comments. The signature of every 4th item is completely different (div.ad-unit vs div.comment). Homogeneity score drops significantly even though the container is the real UGC region. A reply thread with no ads scores higher. Both the ancestor penalty and depth homogeneity are hurt by this — you'd need an "ad-blind" homogeneity that ignores known advertising elements.

6 The Reply Keyword Feature — Should It Exist?

Yes. And it's different from everything discussed above. Both homogeneity approaches try to infer structure from the DOM shape. The reply keyword feature reads semantic signals — what the developer or platform named this region.

How to Use It as a Feature

The keyword feature should produce a continuous score from 0 to 1 rather than a hard binary, because partial signals are common. 

function replyContextScore(element) {
  let score = 0;
  const STRONG_REPLY_TOKENS = [
    'reply', 'replies', 'reply-list', 'reply-thread',
    'child-comment', 'nested-comment', 'sub-comment'
  ];
  const WEAK_REPLY_TOKENS = [
    'children', 'thread', 'nested', 'indent', 'depth'
  ];

  // Own class/id
  const ownTokens = (element.className + ' ' + element.id).toLowerCase();
  if (STRONG_REPLY_TOKENS.some(t => ownTokens.includes(t))) score += 0.6;
  else if (WEAK_REPLY_TOKENS.some(t => ownTokens.includes(t)))  score += 0.2;

  // data-depth attribute
  const depth = parseInt(element.dataset.depth, 10);
  if (!isNaN(depth) && depth > 0) score += Math.min(0.3, depth * 0.1);

  // data-parent-id / data-reply-to present → this node is itself a reply
  if (element.dataset.parentId || element.dataset.replyTo) score += 0.4;

  // ARIA label
  const aria = (element.getAttribute('aria-label') || '').toLowerCase();
  if (/repl(y|ies)/.test(aria)) score += 0.5;

  // Sibling text node: "X replies" immediately before/after this element
  const siblingText = getSiblingText(element).toLowerCase();
  if (/\d+\s*repl(y|ies)/.test(siblingText)) score += 0.4;

  return Math.min(1.0, score);
}

// Use in candidate scoring: a high reply context score LOWERS the UGC region score
// but does NOT zero it out — the container is still UGC, just a sub-region
const ugcScore = baseUGCScore * (1 - replyContextScore * 0.5);

Inner ul.replies with 8 replies High (0.93) High (0.75) ✓ Downweighted

Insight The reply keyword feature works because it's orthogonal to homogeneity. A reply container can be both highly homogeneous AND clearly labelled as a reply context. Using both features together in the model lets it learn the interaction: high homogeneity + low reply-context = primary UGC region. High homogeneity + high reply-context = sub-region.

Caveats on Keyword Matching

Obfuscated class names Sites that use CSS Modules, Tailwind, or CSS-in-JS (styled-components) produce class names like _3xYzt, sc-bdfxgF, or hashed strings. These carry zero semantic signal. For these sites, only structural and data-attribute signals work. The reply keyword feature should degrade gracefully to a score of 0, not break the pipeline.
Internationalisation The word "reply" only exists in English. A Spanish site uses "respuestas", French uses "réponses", German "Antworten". Either the keyword list must be expanded for each language, or you should detect the page language and apply a localised list — otherwise the feature silently fails on non-English sites.

7 Verdict — What to Build

Recommended Architecture

Neither approach alone is sufficient. The right solution layers three signals, each addressing a different failure mode:

Signal 1 — Reply Context Score (new feature)

Extract from class names, IDs, data attributes, ARIA labels, and sibling text. Returns 0–1. Used as a negative modifier on the UGC score for the element. This is the most impactful single change. It directly encodes developer intent about what the container is for.

Signal 2 — Depth-Windowed Homogeneity (replace current flat homogeneity)

Measure child uniformity at depth 1 (weight 1.0), depth 2 (weight 0.5), depth 3 (weight 0.25). Normalise to 0–1. Replace or augment the current single-level homogeneity feature. Tolerates developer variation at depth 3+ by design. Requires model retraining.

Signal 3 — Ancestor Penalty (keep as a tie-breaker, not primary logic)

Keep the current ×0.6 multiplier but only apply it when a candidate has an ancestor that scores above the positive threshold (not just above UGC_LOW_THRESHOLD). This prevents weak outer containers from triggering false penalties, while still handling clear nesting cases.

Implementation Priority

  1. Now (no retraining): Add replyContextScore() as a post-hoc modifier in classify() — same location as the ancestor penalty. Multiply candidate score by (1 - replyContextScore * 0.5). Test on a few sites.
  2. Next training run: Add depth-windowed homogeneity as an additional feature in the feature extractor. Keep the old flat homogeneity feature too — let the model learn which to weight. Export new labeled data confirming the outer list as ground truth.
  3. After validation: Raise the ancestor penalty threshold from UGC_LOW_THRESHOLD to positive_threshold to reduce false penalty triggers.
